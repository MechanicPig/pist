# 本地记录与表格同步设计

本文记录截至 2026-10-10 已讨论确认的数据管理方向，供后续实现时复查。设计约定与已实施部分分别说明，不将已确定的设计视为功能已经实现。

## 目标与现状

本地数据作为主要数据源，腾讯智能表格作为公开数据的载体。支持先将已有表格数据同步到本地，再在本地补充表格缺少的字段；本地字段可以留空，不要求所有信息都适合公开。个人网站属于后续展示方向，应在记录模型和公开数据边界稳定后推进。

表格仍将地图身份与体验记录放在同一行，以 Mod 元数据名和地图名的组合作为地图识别依据。本地已支持同一地图的多条记录，记录使用独立编号与精确远端关联；但尚未建立独立的稳定地图身份，也未完成分阶段统计，改名、路径移动、跨 Mod 迁移及地图翻新的关联仍需后续设计。

## 地图与体验记录

地图身份和体验记录身份需要分开：地图描述体验对象，记录描述在某个时间点或时间段首次体验了这张地图的哪些内容。一张地图可以关联多条记录，不能仅因为地图相同就拒绝新增记录或自动合并。

“初见”与具体存档无关，也不限定为第一次打开地图或第一次游玩会话，而是首次攻略地图内容的过程。补收集品、补充挑战也可以属于首次体验地图的某一部分。表格应反映不同时间点首次体验了哪些地图内容。

连续或时间相近的分次攻略可以更新原记录；时间跨度较大的后续首次体验可能需要新增记录，由用户决定，不按固定时间阈值自动拆分。未通关后继续攻略和通关后补收集品不必采用两套不同的记录规则。

| 场景 | 记录处理原则 |
| --- | --- |
| 同一次攻略中分多次完成地图 | 可以更新原记录 |
| 很久后继续未完成的部分 | 可以新增记录，也可以更新原记录，由用户选择 |
| 很久后首次完成剩余收集品或额外挑战 | 可以新增记录，反映这一阶段的首次体验 |
| 普通重玩已经体验过的内容 | 不应自动新增初见记录，也不应覆盖原记录的死亡数和用时 |
| 地图发生小幅更新 | 通常可以忽略，不因此自动建立新地图身份 |
| 地图设计大幅翻新，实质上成为另一张地图 | 需要考虑新的地图身份，不能仅凭名称相同视为原地图 |
| 地图改名、移动路径或迁移到另一 Mod | 不应仅凭标识变化认定为新地图，需要处理身份关联 |

地图路径、Mod 元数据名和地图名都可以用于识别或匹配，但不应直接等同于永不变化的地图身份。具体身份方案与改名、迁移后的关联方式尚待确定。

## 正式记录编号

正式体验记录使用数字编号，表示这是按实际打图顺序排列的第几条记录。编号属于记录而不是地图，同一地图的不同记录具有不同编号；稳定身份由内部 `local_id` 承载，编号不作为身份键。

先从已有表格同步一次历史数据，按既有行顺序建立记录编号与表格行的关联。后续新增正式记录沿用已有最新编号继续自增。更新原记录保留原编号，不因地图改名或显示名称变化重新编号。

本地记录与表格均应按实际打图顺序排列，而非固定登记顺序。漏登记或误先登记后玩的地图时，允许用户明确调整已通关记录的行位置以恢复实际顺序；普通内容同步不自动重排。行号可以辅助初次导入和定位，但记录编号与行号应明确区分。

当前用 `local_id` 定位本地记录，用 `record_number` 表示体验顺序编号，新记录从计数器继续分配；编号写入表格数字列“编号”，视图按其升序自动排序并隐藏该列。远端关联保存文件 ID、子表 ID 与 API 记录 ID，后续更新不依赖行号、编号或地图名称。

### 顺序修正

记录列表支持左键按住已编号记录行并拖到另一条已编号记录：向上拖动移到目标之前，向下拖动移到目标之后。释放后弹出移动位置及受影响编号的确认窗口；确认前不改变数据，取消或按 Esc 保留原顺序。表头拖动用于调整列宽；释放到表头、空白、表格外、未编号行或原位置时不调整，也不因拖动后的点击打开编辑器。筛选与滚动后的拖动使用稳定记录 ID 定位，并基于完整记录序列预览，包括受影响的隐藏记录，不仅重排可见子集。

拖动过程中直接在列表内预览最终排列：源记录随鼠标移到目标位置，其他记录相应让位，所有记录的编号和内容暂时保持原值。释放后进入确认窗口；取消、按 Esc、移到无效位置或刷新筛选时恢复原排列。预览仅影响显示，不修改本地数据或触发表格写入。

“调整顺序”按钮保留为键盘入口：输入目标记录编号，将选中记录移到该记录之前或之后。两种入口共用同一预览、事务提交和同步流程。例如实际体验 A → B，却先登记 B 再登记 A，可将 A 移到 B 前面。仅重排受影响区间，保留该区间已有编号集合及其他记录的相对顺序，不压缩删除产生的编号空缺；未编号登记仍在末尾，不能参与编号移动。

本地调整通过独立事务接口完成，不开放普通编辑任意修改编号；内部主键、地图数据、存档归属、远端记录 ID、确认基准与编号计数器均保持不变。确认时重新核对完整已编号顺序，过期预览不得直接提交。编号已属于公开字段，调整后的受影响记录标为待推送，再通过现有批量核对、冲突选择和写入响应校验流程同步。网络或写入失败时保留本地新顺序及待推送状态，不回滚已确认的本地调整；缺少数字编号列时不能报告编号同步成功。仅修改本地编号不刷新最近核对时间。

SQLite 结构保持不变：`records.record_number` 仍是可空、正整数、唯一列；语义由不可修改的登记序号改为允许明确修正的体验顺序编号。此语义变更已获用户确认，现有数据无需重排或重写；启用前已确认无记录写入工作流占用，并通过 SQLite backup API 备份及完整性检查。任何实际顺序调整均须由用户在 UI 中确认，不自动修改历史编号。

表格显示顺序通过编号升序自动排序视图反映，不物理移动行，不通过交换行内容或删除再新增模拟移动。远端编号纳入字段比较及写入响应校验；隐藏列仍属于协议字段。普通“采用远端”不会单条改变本地编号，编号冲突时须采用本地或先取消并通过顺序调整处理，避免唯一编号冲突及隐式整组重排。内容同步确认并不证明远端视图配置正确，正式视图需一次性配置并回查。

用户已选择新增隐藏数字列“编号”，作为本地和表格视图共用的排序依据；编号仍不是记录身份键。2026-10-13 在合成测试文档中新建独立子表“编号排序验证”（`TKaD2B`），不调整现有主表协议。三条合成数据按 B=2、A=1、未开始无编号的顺序插入。通过界面选定编号升序并启用自动排序，API 回查视图 `vabcde` 的 `autoSort=true` 与编号升序规则已持久化；带该 `viewID` 查询返回 A → B → 未开始，空编号位于末尾。不带视图读取仍是插入顺序，因此正式实现须区分视图排序与物理行位置。

## 未开始登记与状态选择

允许登记尚未产生体验数据的地图。此类登记状态锁定为“未开始”，不分配正式记录 ID，并始终位于表格末尾。地图名称、Mod 信息等登记资料本身不意味着已经开始体验。

空数据存档默认且锁定为“未开始”。非空数据存档的状态由用户自己填写，不根据读取到的数据自动判定为“进行中”或“已通关”。这是登记流程的设计要求，空数据的判定与状态锁定仍需实现；当前存储只提供编号分配及已编号记录不能退回未开始的约束。

仅当存在体验数据，并且用户将状态设为“进行中”“已通关”等已开始状态后，才为新增的正式记录分配自增 ID。更新已有正式记录则沿用其 ID。

| 输入或操作 | 状态与编号 |
| --- | --- |
| 空数据存档或仅登记地图 | 锁定未开始，不分配正式 ID |
| 非空数据存档 | 状态由用户填写，不自动推断 |
| 有体验数据且确认为已开始的新记录 | 分配新的正式 ID |
| 更新已有正式记录 | 保留原正式 ID |

交互使用“更新原记录”和“新增记录”两个选项。即使当前同一地图只有一条记录，也不应将更新原记录作为唯一允许的操作。

从地图浏览保存时，同存档已有记录进入新增或更新的选择流程，并优先提供同存档记录作为更新目标。只有其他存档的记录时默认新增，不预选跨存档更新目标；仍允许明确选择原记录进行覆盖。存档编号未知的历史记录不视为同存档，也需要明确选择。选择项展示记录编号、存档编号与创建日期，跨存档或归属未知的更新提示覆盖语义。

跨存档更新暂时只支持覆盖：保留原记录的身份、编号和手填信息，以当前存档的游戏数据和存档编号替换原数据，不累加，也不扣减旧存档数据。存档编号仍为单值；跨存档累加及多存档归属不在本次实现范围内。

当前以同一数据目录的跨进程排他锁防止正常工作流之间的并发覆盖：地图浏览与独立记录列表在进入 UI 前获取锁并保持至退出，记录同步 CLI 共用此锁；被占用时提示并退出，不等待。锁由操作系统持有，异常退出或进程终止后释放，不根据 PID 文件判定；锁文件保留，不手工删除。其他记录写入入口也须使用同一锁。暂不增加记录级 revision 或旧快照比较，因此直接调用存储接口、手工写库等不受此保护；未来需要并行编辑或后台同步时重新设计记录级冲突检测。

没有正式编号不等于没有内部标识：当前未开始记录同样使用 `local_id` 保存、编辑和关联表格行，`record_number` 保持为空，不占用正式编号。

## 历史导入与同步冲突

历史导入应保留已有记录和行顺序，不根据推测拆分历史体验阶段，也不编造缺失的数据。之后的新记录从已有编号继续自增。

后续同步发现冲突时必须展示给用户，不直接覆盖。需要把“是否为同一张地图”和“是否为同一条体验记录”分别判断；仅匹配到相同地图不足以决定更新哪条记录。

冲突展示应使用户能够定位相关记录和表格行，并比较双方的数据。保留上一次确认的远端数据作为同步基准；表格手工修改如何回流本地，应通过明确的选择处理，不自动覆盖。

本地可以拥有表格中没有的字段。字段缺失、明确留空、已有值，以及删除操作的同步语义应分别定义，不能把表格没有某个字段直接解释为清空本地数据。

本地分别保存 `map_name` 和可空的 `video_url`。表格不新增视频列：存在视频时将地图名合成为以地图名显示的视频链接，否则写普通文本；读取时拆回名称和链接，核对时同时比较二者。Mod 名和 GameBanana 地址同样分别由 `mod_name`、`mod_url` 保存，在表格中合成为 Mod 名链接。

## 编辑与同步流程

记录编辑确认后先保存本地，再进入应用级后台同步队列，按保存顺序串行核对、写入和校验写入响应。可以继续编辑其他记录，打开新编辑不会取消旧写入；同一条记录仍在队列中时暂不允许再次编辑，防止旧任务覆盖新修改。同步冲突、离线或恢复选择等待当前编辑结束后再弹出；取消后台同步保留已保存的本地修改和待推送状态，不撤销本地编辑。显式同步和顺序调整先等待已有队列结束，并重新读取本地数据。正常退出应用前须等待队列完成；强制中断时本地记录和不确定新增保护仍保留，不自动重试。记录列表在每条后台处理结束后刷新状态。

本地修改默认同步到配置的表格。打开编辑时不读取远端，使用本地字段配置及最近读取的表格选项作为编辑提示；缓存字段不作为当前远端兼容性的证据。编辑确认后先保存本地，后台提交前才实时读取字段与目标记录，按上次确认基准核对；远端存在未采用的变化时提示选择，不直接覆盖。支持范围使用独立配置文件声明，缺少必需字段或字段类型不匹配时阻止远端同步，不撤销本地保存；额外字段不自动写入或修改。

未配置凭证或读取失败时，保存后的同步流程提供“仅保存本地”“取消”，两者均保留已经保存的本地修改，取消只终止本次同步。选择仅保存本地后，本次运行后续不再重复询问是否允许离线保存；该选择不意味着可以跳过数据冲突，也不永久禁用之后的同步。字段不兼容等问题仍需给出诊断。

本地最新数据与远端确认数据分别保存。连续本地修改只替换最新数据，不推进确认基准，也不保留完整修改历史。例如上次确认数据为 A，本地先修改为 B、再修改为 C，基准仍然是 A：同步时远端仍为 A，可以提交 C；远端已变为 D，则需要展示差异并由用户选择。不能把正常的本地编辑与确认基准之间的差异当作远端冲突。

通过核对后先保存本地，再写入远端；写入失败不撤销本地记录，记录保持待同步。仅在确认远端已接收本次提交内容后更新确认基准。同步期间若本地已有新修改，旧提交的成功只更新远端基准，不能把更新后的本地内容标为已同步。提交前复查不能保证远端原子比较与写入，不应将其描述为事务保证。

记录编辑在确认前只保留内存状态，不持久化独立草稿；取消编辑不改变正式记录。确认仅保存本地后，直接持久化完整记录并标为待同步，新增正式记录按已有规则分配编号。冲突窗口提供“采用本地”“采用远端”“仅保存本地”和“取消”；仅保存本地不写远端、不推进确认基准，也不代表未来重试时已允许覆盖冲突。路线编辑使用独立的草稿存储。

正式编号不得因删除最新记录而复用；已编号记录不得改回未开始。存档编号用于后续阶段用时和死亡数的差值计算，不替代体验记录身份。地图改名、路径移动、跨 Mod 迁移的关联交互另行设计，不在本次同步流程中自动合并。

主房间数只接受正整数或空值，空值表示未统计或没有有效统计值，不使用 `-1` 或 `0` 占位。不想统计的原因由用户在备注中说明，不增加额外状态字段，也不自动补备注。死亡数、草莓数等其他字段的零仍是有效值。采用远端数据时将主房间数的非正数转换为空，但读取快照和确认基准保留原始返回值，避免掩盖远端是否实际接受了清空操作。

`time_played` 在记录模型中使用 `Duration | None`，SQLite 使用非负的 INTEGER .NET ticks（每 tick 为 100 ns），空值与零时长不同；非整 tick 或超出 SQLite 有符号 64 位整数范围的值不允许保存。编辑器统一使用 `Duration` 默认的游戏计时器格式，显示三位毫秒；文本未变时保留原始时长，避免修改其他字段丢失精度，明确改写时按相同格式解析，清空则保存为空。表格编码和核对仍使用截断到整秒的 `H:MM:SS`。采用远端数据时，若整秒文本与本地格式化结果相同，保留本地亚秒数据；远端用时改变则重新解析，清空则保存为空。同步快照和确认基准继续保存表格协议值，不改为 ticks。

2026-10-16 将已有用时文本一次性迁移为 ticks，只转换原本保存的整秒数据，不从当前存档猜补历史亚秒精度；迁移保留编号、关联、确认基准和同步状态，不写远端表格。迁移前备份，事务内重建记录表并校验逐字段内容、外键及数据库完整性，源码不保留旧格式兼容分支。

当时的本地专属字段继续保留，包括内部主键、正式编号、创建时间、地图文件路径、SID、Side、存档编号、英文名称、制作人员与现有游戏难度信息；正式编号在后续顺序修正中已作为隐藏数字列同步。存档中的 `completed` 与手动填写的 `status` 保持独立。分阶段用时归属的新增字段暂缓，不混入此次迁移。

### 只读数据与同步基准

公式列包括平均单面死亡数、平均单面用时、草莓数、平均单面用时（秒）、用时（秒）和体感难度权重。它们随完整远端行保存，不直接编辑或写回。API 未返回有效结果时保存实际返回的空值或缺失情况，不编造计算结果，也不将缺失解释为零。

最近读取的完整远端行与上次确认的同步基准分别保存。读取到冲突数据可以更新读取快照，但不能推进确认基准；读取本身不等于确认。远端相对基准发生变化但已与本地待写值一致的字段不构成冲突；其他变化仍须核对。重新核对后所有待写字段均与远端一致时，可直接确认并标记已同步，刷新确认基准而不重写表格；不一致时写入并校验响应，基准仅覆盖已提交且验证的字段，未提交字段沿用写前读取值，不把写入响应伪装成完整读取快照。

记录列表的状态文案使用“无本地变更”“待推送”“待核对”，分别对应本地与确认基准一致、本地修改尚未确认写入远端、缺少可靠核对基准或操作结果尚待核对；这些状态不表示程序持续监测远端变化。“最近核对时间”作为独立列显示每条记录最近一次确认远端数据的时间，按系统本地时区展示，支持拖动列宽并保存配置；没有确认时间时显示“尚未核对”。本地编辑、刷新列表或仅读取远端快照不推进该时间，内部状态值和数据库结构不变。

记录列表提供“一键同步”，按正式编号顺序核对全部本地记录，不受当前搜索、筛选或本地同步状态影响；全部无本地变更时仍允许执行，以发现远端变化。处理期间显示进度并禁止重复操作；远端变更和未确认新增沿用单条同步的人工选择流程。取消、仅保留本地或核对失败时停止后续处理，保留已完成结果，并刷新本地列表；完成计数仅包含本次实际处理且已确认的记录，不以未处理记录的旧状态冒充本次成功。

单条已关联记录按远端 `recordID` 查询核对，不依赖行位置。每次查询仍检查最新字段结构，目标记录缺失时阻止写入，不自动新增代替。2026-10-14 起常规写后回读移至在线测试：新增和更新接口的成功响应返回记录 ID 与内容，运行时按提交 ID、字段完整性及规范化后的值确认，不只看成功码。单选及多选响应可能使用选项 ID；遇到未知 ID 时，仅额外读取一次字段配置，不读取记录或重写，字段结构变化、刷新失败或仍未知时不确认。

一键同步共享首次完整表格快照：全部记录一致时只读取一次；已有记录的修改先保存本地并排队，每批最多 100 条，提交前只查询当前批次的 ID 进行核对，调用批量更新后按响应独立确认每行。正常情况下 k 条已有记录更新需要一次完整表格读取、ceil(k / 100) 次局部读取及 ceil(k / 100) 次更新请求；底层表格定位、字段查询和记录分页可能对应多次 API 调用。未知选项 ID 的整批响应最多额外读取一次字段配置。批量响应缺失或不符的行仍待同步，有效行立即确认，后续失败或进程退出不撤销已完成的确认。未绑定记录匹配、首次新增复核与不确定新增恢复仍查询完整表格；冲突或新增恢复交互后刷新快照，不继续使用交互前的数据。排队、请求已发起与响应校验成功是不同阶段，未通过校验的结果保持待同步，失败不自动重试。

起始日期、结束日期与更新时间均为纯日期：本地模型使用 `date`，SQLite 保存 `YYYY-MM-DD`，表格时间戳按系统本地时区解码后提取年月日，写出时编码为对应日期的本地零点。日期选择器默认“今天”、地图更新时间的日期提取和记录创建日期的显示也使用本地时间，创建时间戳仍以 UTC 保存；不硬编码 UTC+8，也不将当前时区偏移套用于其他日期。旧规则导入或写出的存量日期需单独核对，不自动整体加减一天。复选框在表格读取边界将空值解码为 `False`；本地磁带字段为默认 `False` 的非空布尔值，编辑界面只提供有／无，不保留未知状态，也不在比较层另设空值特判。
