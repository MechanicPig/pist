# 本地记录与表格同步设计

本文记录截至 2026-10-10 已讨论确认的数据管理方向，供后续实现时复查。设计约定与已实施部分分别说明，不将已确定的设计视为功能已经实现。

## 目标与现状

本地数据作为主要数据源，腾讯智能表格作为公开数据的载体。支持先将已有表格数据同步到本地，再在本地补充表格缺少的字段；本地字段可以留空，不要求所有信息都适合公开。个人网站属于后续展示方向，应在记录模型和公开数据边界稳定后推进。

表格仍将地图身份与体验记录放在同一行，以 Mod 元数据名和地图名的组合作为地图识别依据。本地已支持同一地图的多条记录，记录使用独立编号与精确远端关联；但尚未建立独立的稳定地图身份，也未完成分阶段统计，改名、路径移动、跨 Mod 迁移及地图翻新的关联仍需后续设计。

## 地图与体验记录

地图身份和体验记录身份需要分开：地图描述体验对象，记录描述在某个时间点或时间段首次体验了这张地图的哪些内容。一张地图可以关联多条记录，不能仅因为地图相同就拒绝新增记录或自动合并。

“初见”与具体存档无关，也不限定为第一次打开地图或第一次游玩会话，而是首次攻略地图内容的过程。补收集品、补充挑战也可以属于首次体验地图的某一部分。表格应反映不同时间点首次体验了哪些地图内容。

连续或时间相近的分次攻略可以更新原记录；时间跨度较大的后续首次体验可能需要新增记录，由用户决定，不按固定时间阈值自动拆分。未通关后继续攻略和通关后补收集品不必采用两套不同的记录规则。

| 场景 | 记录处理原则 |
| --- | --- |
| 同一次攻略中分多次完成地图 | 可以更新原记录 |
| 很久后继续未完成的部分 | 可以新增记录，也可以更新原记录，由用户选择 |
| 很久后首次完成剩余收集品或额外挑战 | 可以新增记录，反映这一阶段的首次体验 |
| 普通重玩已经体验过的内容 | 不应自动新增初见记录，也不应覆盖原记录的死亡数和用时 |
| 地图发生小幅更新 | 通常可以忽略，不因此自动建立新地图身份 |
| 地图设计大幅翻新，实质上成为另一张地图 | 需要考虑新的地图身份，不能仅凭名称相同视为原地图 |
| 地图改名、移动路径或迁移到另一 Mod | 不应仅凭标识变化认定为新地图，需要处理身份关联 |

地图路径、Mod 元数据名和地图名都可以用于识别或匹配，但不应直接等同于永不变化的地图身份。具体身份方案与改名、迁移后的关联方式尚待确定。

## 正式记录编号

正式体验记录使用自增数字作为 ID，表示这是第几条记录。编号属于记录而不是地图，同一地图的不同记录具有不同编号。

先从已有表格同步一次历史数据，按既有行顺序建立记录编号与表格行的关联。后续新增正式记录沿用已有最新编号继续自增。更新原记录保留原编号，不因地图改名或显示名称变化重新编号。

用户目前约束已通关的表格行不调整位置。历史导入与后续同步需要保留这一约束，不能为了重新排序或整理编号而移动已通关记录。行号可以辅助初次导入和定位，但记录编号与行号应明确区分。

当前用 `local_id` 定位本地记录，用 `record_number` 表示正式自增编号；后者不写入表格独立列。远端关联保存文件 ID、子表 ID 与 API 记录 ID，后续更新不依赖行号或地图名称。是否公开正式编号可另行评估，不阻塞现有同步。

## 未开始登记与状态选择

允许登记尚未产生体验数据的地图。此类登记状态锁定为“未开始”，不分配正式记录 ID，并始终位于表格末尾。地图名称、Mod 信息等登记资料本身不意味着已经开始体验。

空数据存档默认且锁定为“未开始”。非空数据存档的状态由用户自己填写，不根据读取到的数据自动判定为“进行中”或“已通关”。这是登记流程的设计要求，空数据的判定与状态锁定仍需实现；当前存储只提供编号分配及已编号记录不能退回未开始的约束。

仅当存在体验数据，并且用户将状态设为“进行中”“已通关”等已开始状态后，才为新增的正式记录分配自增 ID。更新已有正式记录则沿用其 ID。

| 输入或操作 | 状态与编号 |
| --- | --- |
| 空数据存档或仅登记地图 | 锁定未开始，不分配正式 ID |
| 非空数据存档 | 状态由用户填写，不自动推断 |
| 有体验数据且确认为已开始的新记录 | 分配新的正式 ID |
| 更新已有正式记录 | 保留原正式 ID |

交互使用“更新原记录”和“新增记录”两个选项。即使当前同一地图只有一条记录，也不应将更新原记录作为唯一允许的操作。

从地图浏览保存时，同存档已有记录进入新增或更新的选择流程，并优先提供同存档记录作为更新目标。只有其他存档的记录时默认新增，不预选跨存档更新目标；仍允许明确选择原记录进行覆盖。存档编号未知的历史记录不视为同存档，也需要明确选择。选择项展示记录编号、存档编号与创建日期，跨存档或归属未知的更新提示覆盖语义。

跨存档更新暂时只支持覆盖：保留原记录的身份、编号和手填信息，以当前存档的游戏数据和存档编号替换原数据，不累加，也不扣减旧存档数据。存档编号仍为单值；跨存档累加及多存档归属不在本次实现范围内。

当前以同一数据目录的跨进程排他锁防止正常工作流之间的并发覆盖：地图浏览与独立记录列表在进入 UI 前获取锁并保持至退出，记录同步 CLI 共用此锁；被占用时提示并退出，不等待。锁由操作系统持有，异常退出或进程终止后释放，不根据 PID 文件判定；锁文件保留，不手工删除。其他记录写入入口也须使用同一锁。暂不增加记录级 revision 或旧快照比较，因此直接调用存储接口、手工写库等不受此保护；未来需要并行编辑或后台同步时重新设计记录级冲突检测。

没有正式编号不等于没有内部标识：当前未开始记录同样使用 `local_id` 保存、编辑和关联表格行，`record_number` 保持为空，不占用正式编号。

## 历史导入与同步冲突

历史导入应保留已有记录和行顺序，不根据推测拆分历史体验阶段，也不编造缺失的数据。之后的新记录从已有编号继续自增。

后续同步发现冲突时必须展示给用户，不直接覆盖。需要把“是否为同一张地图”和“是否为同一条体验记录”分别判断；仅匹配到相同地图不足以决定更新哪条记录。

冲突展示应使用户能够定位相关记录和表格行，并比较双方的数据。保留上一次确认的远端数据作为同步基准；表格手工修改如何回流本地，应通过明确的选择处理，不自动覆盖。

本地可以拥有表格中没有的字段。字段缺失、明确留空、已有值，以及删除操作的同步语义应分别定义，不能把表格没有某个字段直接解释为清空本地数据。

本地分别保存 `map_name` 和可空的 `video_url`。表格不新增视频列：存在视频时将地图名合成为以地图名显示的视频链接，否则写普通文本；读取时拆回名称和链接，核对时同时比较二者。Mod 名和 GameBanana 地址同样分别由 `mod_name`、`mod_url` 保存，在表格中合成为 Mod 名链接。

## 编辑与同步流程

本地修改默认同步到配置的表格。打开编辑时先读取远端，提交修改前再次读取核对，避免编辑期间的远端变化被忽略。远端读取成功后检查支持字段的名称和类型；支持范围使用独立配置文件声明。缺少必需字段或字段类型不匹配时阻止远端同步，不阻止仅保存本地；额外字段不自动写入或修改。

未配置凭证或读取失败时，提供“仅保存本地”“取消”。选择仅保存本地后，本次运行后续不再重复询问是否允许离线保存；该选择不意味着可以跳过数据冲突，也不永久禁用之后的同步。字段不兼容等问题仍需给出诊断。

本地最新数据与远端确认数据分别保存。连续本地修改只替换最新数据，不推进确认基准，也不保留完整修改历史。例如上次确认数据为 A，本地先修改为 B、再修改为 C，基准仍然是 A：同步时远端仍为 A，可以提交 C；远端已变为 D，则需要展示差异并由用户选择。不能把正常的本地编辑与确认基准之间的差异当作远端冲突。

通过核对后先保存本地，再写入远端；写入失败不撤销本地记录，记录保持待同步。仅在确认远端已接收本次提交内容后更新确认基准。同步期间若本地已有新修改，旧提交的成功只更新远端基准，不能把更新后的本地内容标为已同步。提交前复查不能保证远端原子比较与写入，不应将其描述为事务保证。

不再保存独立的记录编辑草稿。取消编辑不改变正式记录；确认仅保存本地后，直接持久化完整记录并标为待同步，新增正式记录按已有规则分配编号。冲突窗口提供“采用本地”“采用远端”“仅保存本地”和“取消”；仅保存本地不写远端、不推进确认基准，也不代表未来重试时已允许覆盖冲突。路线编辑的草稿不受此调整影响。

正式编号不得因删除最新记录而复用；已编号记录不得改回未开始。存档编号用于后续阶段用时和死亡数的差值计算，不替代体验记录身份。地图改名、路径移动、跨 Mod 迁移的关联交互另行设计，不在本次同步流程中自动合并。

## 后续待设计事项

- 地图的稳定身份及其匹配机制：如何关联改名、移动路径和跨 Mod 迁移，如何处理实质性翻新的地图。
- 空数据的判定与未开始状态锁定，以及登记转为正式记录时的体验数据校验。
- 同一地图多条记录的阶段内容如何表达；更新目标选择与跨存档覆盖流程已实现，不再列为待确定事项。
- 分阶段记录的死亡数和用时：存档数据可能是累计值，如何使用阶段基线、差值或人工确认避免重复计入；不能直接将同一累计值复制到多条记录。
- 未开始登记转为正式记录后的表格插入或移动方式：同时满足未开始项始终在末尾、已通关行不调整位置的约束。
- 未关联远端行的后续导入及通用缺失关联修复，明确人工确认与去重方式；不确定新增已有专用恢复流程。

## 本地记录列表

记录列表的列宽保存在 `.pist/settings.json` 的 `record_list_max_widths` 中：`record_number` 默认为 6，`map_name` 默认为 40，`mod_name` 默认为 32，`status` 默认为 12，`save_slot` 默认为 6，`sync_state` 默认为 8。宽度按终端显示列计量，须为正整数；各列按配置宽度显示，超过上限显示省略号，搜索和编辑仍使用完整值。地图浏览与独立记录列表共用该配置。左键拖动表头右侧分隔线实时调整宽度，最小为 4，松开后保存；保存失败提示并恢复原宽度。手工修改配置后重新启动生效。

`pist records browse` 独立打开历史记录，不读取游戏、Mod 或存档；地图浏览内按 `r` 打开同一列表。列表按正式编号排序，未编号登记放在最后；支持搜索编号、地图、Mod 和状态，以及筛选待同步或待核对的记录。`pist records sync <local_id>` 为原同步命令的统一命名，不再使用单数 `record`。

列表按内部 `local_id` 编辑明确选中的记录，不重新匹配地图或读取当前游戏统计，不改变记录归属或正式编号。完整字段编辑、同步冲突和不确定新增恢复交互集中在 `ui.records`，地图浏览与独立列表共用同一控制器和领域服务。同步重试仍先核对远端，冲突须明确选择；取消或选择仅保留本地时不写远端。列表编辑确认仅保存本地后保持待同步。

独立列表在读取记录前取得同一跨进程写入锁，并保持到退出，因此不能与地图浏览或记录同步 CLI 同时写入。此次仅新增列表查询，不改变 SQLite schema，不迁移已有数据。

## 首次历史导入

2026-10-04 的只读快照包含主表 166 条记录；用户已确认 API 返回顺序与表格界面顺序一致。本次据此建立正式编号 1–166，后续新增正式记录从 167 继续。此确认仅用于首次历史编号，后续关联使用文件、子表与 API 记录 ID，不重新依赖行号。

仅本次导入采用表格非空值优先，表格缺失的字段用无歧义的本地数据补充。35 条原本地记录对应 29 条表格记录；4 组重复或过程快照归并到同一记录，包括宝石神殿的进行中与通关快照。另有 2 条由旧 Dialog 识别问题造成的名称差异，按表格名称修正。其余 137 条仅来自表格，不虚构地图路径、SID、Side 或存档槽；一条缺失的 Mod 元数据名也保持为空。

首次导入当时仅落地可空来源信息、正式编号、表格关联和按内部主键更新的存储接口；双向同步与冲突确认随后已实现，进度见下文。此次表格优先策略仅适用于首次导入，不是长期覆盖规则。

## 同步持久化实施进度

2026-10-10 已落地确认基准、同步状态和独立编号计数器的存储接口。每次本地保存将最新记录标为待同步；确认接口保留提交期间产生的新修改。记录编辑草稿曾作为离线暂存方案，现已移除，统一使用待同步记录。

现有 166 条记录保持编号、内容与远端关联不变，确认基准来自首次导入的原始只读快照，而非经过本地补充的数据。所有历史记录初始为待核对，不因存在旧快照就视为当前远端已经一致。迁移前已备份数据库，其他业务表不变，未读写远端；一次性迁移脚本仅保留在忽略目录 `.pist/scripts/`。

支持字段配置位于 `pist/src/pist/data/sheet_fields.toml`；规则仅写入已声明且可写的字段，不修改额外列或公式列。领域服务按已关联的远端记录 ID 更新，缺失关联行不自动转为新增；写入后回读确认，读取失败或内容不符时保留待同步。新增后已返回的记录 ID 会先保存，即使回读失败也不会再次新增；未返回 ID 且远端已有同名记录时阻止自动重试，需另行核对关联。

### 只读数据与同步基准

公式列包括平均单面死亡数、平均单面用时、草莓数、平均单面用时（秒）、用时（秒）和体感难度权重。它们随完整远端行保存，不直接编辑或写回。API 未返回有效结果时保存实际返回的空值或缺失情况，不编造计算结果，也不将缺失解释为零。

最近读取的完整远端行与上次确认的同步基准分别保存。读取到冲突数据可以更新读取快照，但不能推进确认基准；读取本身不等于确认。远端相对基准发生变化但已与本地待写值一致的字段不构成冲突；其他变化仍须核对。重新核对后所有待写字段均与远端一致时，可直接确认并标记已同步，刷新确认基准而不重写表格；不一致时仍需写入并回读确认。

记录列表提供“一键同步”，按正式编号顺序处理全部待核对、待同步记录，不受当前搜索与筛选影响，跳过已同步记录。处理期间显示进度并禁止重复操作；远端变更和未确认新增沿用单条同步的人工选择流程。取消、仅保留本地或核对失败时停止后续处理，保留已完成结果，并刷新本地列表。

单条已关联记录按远端 `recordID` 查询核对和写后回读，不依赖行位置。每次查询仍检查最新字段结构，目标记录缺失时阻止写入，不自动新增代替。

一键同步共享首次完整表格快照：全部记录一致时只读取一次；已有记录的修改先保存本地并排队，每批最多 100 条，提交前只查询当前批次的 ID 进行核对，调用批量更新后立即按 ID 回读确认。正常情况下 k 条已有记录更新需要一次完整表格读取、2 × ceil(k / 100) 次局部读取及 ceil(k / 100) 次更新请求；底层表格定位、字段查询和记录分页可能对应多次 API 调用。后续批次失败或进程退出不撤销前批已完成的确认。未绑定记录匹配、首次新增复核与不确定新增恢复仍查询完整表格。冲突或新增恢复交互后刷新快照，不继续使用交互前的数据，也不以局部回读替代用于匹配的完整快照。排队、已提交与回读确认是不同阶段，前两者均保持待同步；失败不自动重试，也不得报告未确认记录同步成功。

起始日期、结束日期与更新时间均为纯日期：本地模型使用 `date`，SQLite 保存 `YYYY-MM-DD`，表格时间戳按系统本地时区解码后提取年月日，写出时编码为对应日期的本地零点。日期选择器默认“今天”、地图更新时间的日期提取和记录创建日期的显示也使用本地时间，创建时间戳仍以 UTC 保存；不硬编码 UTC+8，也不将当前时区偏移套用于其他日期。旧规则导入或写出的存量日期需单独核对，不自动整体加减一天。复选框在表格读取边界将空值解码为 `False`；本地磁带字段为默认 `False` 的非空布尔值，编辑界面只提供有／无，不保留未知状态，也不在比较层另设空值特判。
