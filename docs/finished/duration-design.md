# Duration 设计回顾

> 状态：改造已完成，核心结论仍有效。本文保留演进、方案取舍和验证记录，不替代当前 API 使用说明；后续设计取代其核心结论时移入 archive。

本文记录 2026-10-16 至 2026-10-17 的时长模型改造：从存档专用的整毫秒包装，收敛为精确时长值类型，并分离存档编码、游戏计时精度、显示格式和应用持久化。使用示例见 [Berries 使用说明](../berries-usage.md#构造与解析时长)，记录存储与同步约定见 [数据管理设计](../data-management-design.md)。

## 背景与问题

旧版 `Duration` 的构造参数实际是存档中的 .NET ticks，内部却只保存整毫秒，并限制非负数。非整毫秒数据曾被直接视为错误，比早期实现中的警告行为更严格；既可能阻断读取，也不能完整保留原始数据。旧代码中的 `filetime` 命名还混淆了时间间隔与带纪元的时间戳：这里处理的是 .NET TimeSpan 的 100 ns ticks，不是日期时间。

游戏计时采用约定的 17 ms 增量，但“是否符合游戏计时精度”不同于“能否表示这段时长”。构造时直接拒绝或校正数据，会使手工修改或损坏的存档难以检查，也把游戏语义耦合进底层数值类型。

另一个问题是显示与存储边界混杂。表格要求的固定 `H:MM:SS` 曾混入公共游戏格式接口，导致游戏秒级展示行为被改变；本地记录保存格式化文本，也让显示精度反过来限制存储精度。预览中还存在后端转 ticks、前端再计算和格式化的重复处理。

改造目标因此明确为：先完整保留时长，再显式转换、检查和对齐；格式化只产生展示文本，不修改原始值。

## 方案演进

### 从整毫秒改为无损存储

第一阶段先修正异常数据的读取行为，再保存完整 ticks，提供计时帧构造、精度检查和对齐操作。随后允许底层时长为负数，是否符合业务要求交由使用方检查。累计值与分量的命名也逐步分开，避免 `milliseconds` 同时表示整段时长和毫秒分量。

### 尝试按精度区分类型

曾参考 C++ `chrono`，尝试用“计数 × 周期”表达时长，分别提供 `TickDuration` 和 `FrameDuration`，共享运算和转换逻辑；同时把 `timedelta` 视为微秒精度的外部时长。

这个方案暴露了新的问题：周期由类变量决定时，继承可能改变单位语义；把周期放到实例后，不同类型又只是同一段时长的不同表示。为了单位差异维护类型层级、运算返回类型和跨类型相等性，设计成本超过了当前需求的收益。

最终撤掉这些子类，统一使用一个精确的 `Duration`。ticks、计时帧和微秒只是输入输出单位，不决定类型身份；游戏精度通过显式对齐表达，不再需要另一种时长类型。

### 回归标准数据类与显式边界

构造过程中曾尝试自行实现 `__init__` 并转发给 `Fraction`，最终恢复 dataclass 生成的构造方法：直接构造接受内部表示，转换入口承担数值转换。相等性、哈希、排序和 `repr` 也使用 dataclass 的实现，不额外维护一套数值协议。

与 `timedelta` 的混合运算和相等比较最终移除，只保留显式转换，避免跨类型相等性、哈希契约和精度处理变复杂。

## 最终实现

### 精确、有符号的值模型

`Duration` 是 `frozen=True`、`slots=True`、`order=True` 的 dataclass，唯一数据字段为 `total_seconds: Fraction`。它可以精确表达负值、100 ns ticks、17 ms 计时增量，以及 `1/3` 秒等不能用有限小数表示的时长。

`Duration()` 构造零值；直接构造只接受 `Fraction`，由 `__post_init__` 检查实际类型。`from_seconds()` 使用 Fraction 的转换和比值语义，不提供默认数值；`from_units()` 用关键字参数累加小时、分钟、秒及各种亚秒单位，不限制输入为常规分量范围。浮点输入保留其精确二进制值，需要精确十进制时应显式使用字符串或 `Fraction`。

基础分量为 `hours`、`minutes`、`seconds`、`subseconds`、`milliseconds`，按绝对时长计算，符号由整体值表达。`hours` 不按天回绕；分钟和秒为 0–59，毫秒为 0–999，`subseconds` 保留精确的不足一秒部分。

### 运算、转换与对齐

时长加减只接受 `Duration`；数值乘除表示缩放；两个时长相除返回精确比值。另提供整除、余数、`divmod()`、一元正负号、绝对值和真值判断。整数不能直接作为时长参与加减，`timedelta` 也不隐式参与运算。

| 接口 | 契约 |
| --- | --- |
| `from_dotnet_ticks()` / `to_dotnet_ticks()` | 与 100 ns 的 .NET TimeSpan ticks 转换，不涉及纪元 |
| `from_timer_frames()` / `to_timer_frames()` | 与名义 17 ms 计时增量转换，不是录像帧或严格的 1/60 秒 |
| `from_timedelta()` / `to_timedelta()` | 显式转换，保留微秒精度；转换到 timedelta 时还受其范围限制 |
| `is_aligned(quantum)` | 检查是否为指定正精度的整数倍 |
| `floor()` / `ceil()` / `trunc()` / `round()` | 返回对齐后的新值，不修改原值 |

转换要求精确可表示，不能整除目标单位时抛出异常，不隐式舍入。需要损失精度时，调用方先明确选择对齐方式：`floor` 向负无穷取整，`ceil` 向正无穷取整，`trunc` 向零截断，`round` 就近舍入、恰好中点取偶数倍。对齐使用正的有理数精度，不局限于预定义单位。

### 格式化与解析

移除 `DurationParts` 和旧的专用游戏格式方法，统一通过 `format(value, spec)` 与 `Duration.from_format(text, spec)` 处理。实现集中在 `berries/game/duration/` 子包：`duration.py` 保存时长模型，`_format.py`、`_parse.py` 分别实现格式化与解析，`__init__.py` 仅提供公共导出。公共入口仍为 `berries.game.duration.Duration`。

格式语法支持时分秒分量、累计单位、小数位数、可选分支和字面量转义。`%H` 保留按天回绕的小时分量含义，累计小时另用 `%Qh`；`%Qm`、`%Qs` 对应累计分钟和秒。小数按指定宽度截断，包括无限循环小数，不改变内部精度。

游戏格式由两个固定格式字符串表达：`GAME_TIMER_FORMAT` 为默认三位毫秒格式，`GAME_TIMER_SECONDS_FORMAT` 为秒级格式。`str(value)`、空格式和默认游戏展示使用同一个默认格式，不再维护不同风格的字符串接口。

反向解析只恢复文本实际包含的精度，不能恢复已经截掉的数据。它要求文本符合格式的规范输出；歧义、矛盾或不匹配的输入抛出 `ValueError`，不猜测解释。表格固定的 `H:MM:SS` 属于应用协议，不作为公共类型的默认格式。

2026-10-18 修复了解析搜索的两个复杂度问题：等价可选分支直到末尾才去重会产生指数级路径，按 token 递归会使长平铺格式耗尽 Python 调用栈。现在按 token 迭代推进不同匹配状态，分支结束立即合并；字段约束按数值语义规范化，同值重复字段不继续增长，矛盾值和首数字为零的主分支提前剪枝。可选分支内部也迭代处理，不依赖全局递归上限；最终仍通过完整重新格式化检查分支、冗余字段与规范文本，并拒绝多个不同值。合并的是相同位置、字段、符号和符号位置的状态，不是任取第一个候选。不对所有合法格式宣称线性复杂度。

本机 Windows／CPython 3.14.7，旧／新实现使用同一输入，各 3 次取中位数：`[%S|%S]` 重复 16 组、输入 32 个零时约为 3.75 秒／0.14 毫秒；新实现解析 `%S:` 重复 2000 组约 9.8 毫秒，不再触发递归溢出。3 类常用短格式各执行 3000 次、重复 3 次，旧实现约 14.5–27.5 微秒／次，新实现约 17.4–38.3 微秒／次；状态归一化和合并有固定成本，这次改进针对复杂格式退化，不宣称所有格式都更快。回归使用长平铺格式和隔离进程中的宽松超时，不依赖上述本机毫秒数；原审查的 15,671 项独立格式、精度与歧义探针仍通过。

随后针对普通格式的固定成本，改为列表推进候选：单一路径不执行状态哈希或去重，同一路径的变长数字候选消费不同长度，也无需去重；字面量匹配保持已有状态的区别。只有可选分支汇合，或多条路径消费数字后可能收敛时才合并；两个候选直接比较，三个及以上才使用哈希集合。重复字段约束和最终规范文本回验仍保留，未因没有可选组就忽略变长数字可能产生的歧义。

与 `9ca00ed` 的全程集合方案对比，本机同一环境中交替执行前／后实现并轮换先后顺序，各 7 轮取中位数；普通用例每轮 3000 次，256 组用例每轮 200 次。计时范围为完整文本解析，包含格式语法解析与最终回验，不含外层 Duration 对象构造。下表单位为微秒／次，仅说明本机样本，默认游戏毫秒格式约持平，不宣称可选分支普遍显著加速。

| 输入／格式 | 全程集合 | 按需合并 | 变化 |
| --- | ---: | ---: | ---: |
| `12:34:56.789`／`%H:%M:%S.%3f` | 27.47 | 25.86 | -5.9% |
| `01:23`／`%M:%S` | 12.53 | 11.73 | -6.5% |
| `123.4567890`／`%Qs.%7f` | 19.25 | 18.04 | -6.3% |
| `123`／`%Qh%M` | 16.27 | 14.91 | -8.3% |
| `12:34:56.789`／默认游戏毫秒格式 | 42.14 | 42.60 | +1.1% |

## Pist 与存档边界的调整

| 边界 | 最终行为 |
| --- | --- |
| 存档读取与 Pydantic | 字段统一使用 `Duration`，文件输入边界将有符号 ticks 解析为时长，写出边界检查精度与 Int64 范围并转换回 ticks；Duration 本身不内置存档协议 |
| 本地体验记录 | `time_played` 使用 `Duration \| None`，SQLite 保存整数 ticks，不保存显示文本；记录层限制非负、整 tick 和有符号 64 位整数范围，空值区别于零 |
| 记录编辑器 | 使用默认游戏格式展示；文本未变时保留原始时长，避免修改其他字段丢失隐藏精度；明确改写时按相同格式解析 |
| 表格编码与核对 | 在表格边界输出截断到秒的 `H:MM:SS`；核对同样按秒级内容进行，不要求本地精度退化为秒 |
| 采用远端用时 | 远端整秒内容与本地格式化结果相同时保留本地亚秒值；远端内容改变时重新解析，清空则保存为空 |
| 地图预览 | 后端直接累加 Duration，最后投影为游戏秒级文本；不再往返转换 ticks，前端不重复累加或格式化 |

本地记录的 schema 和已有数据随存储调整迁移，未保留旧文本字段的运行时兼容层。同步快照与确认基准仍保存表格协议值，不随本地 ticks 存储改变。

## 结果与验证

最终保留一个精确时长值类型，以及显式的单位转换、精度对齐和格式化入口。存档编码不再决定构造语义，游戏精度不再决定底层表示能力，表格格式也不再影响游戏展示。底层允许保留异常或负值供检查，业务层按自身约束决定是否接受。

相关回归覆盖有符号 ticks 往返、有理数与浮点转换、负数对齐和中点取偶、运算类型约束、dataclass 与 Pydantic 契约、格式解析与歧义、SQLite 存储范围、编辑保精度和表格秒级核对。预览测试另覆盖精确累加、零值与缺失值区别、缺失后的累计前缀，以及不能表示为整 tick 的时长；浏览器验证过房间用时与累计用时展示。

这次改造解决的是表达和边界正确性，不以现有验证宣称性能收益。被撤掉的中间方案包括多精度时长子类、`DurationParts`、重复的应用解析包装和前端时间格式化。
