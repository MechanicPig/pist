# 存档 XML 后端选择

> 状态：lxml 后端选型及历史验证已完成，选型结论仍有效。2026-10-22 的[完整建模迁移](saves-modeling.md)已取代下文保留树、片段、未知扩展及最小修改的实现；这些段落仅说明当时方案，不再是当前契约。性能数据只代表文中注明的历史环境与实现。

2026-10-20 更新：下文的文件会话与关闭提交描述是历史实现，已改为一次性 `read()` 与显式 `write()`，不保留文件生命周期。当前契约以 [Saves API](../saves-domain-api.md) 为准；XML 后端比较和原始验证数据仍有效。

存档文件层使用 `lxml.etree`，保留完整 XML 文档并只编辑支持的字段。该选择适用于 `MainSave`、`ModBackupSave` 和 CollabUtils2 内嵌会话；应用已迁移到此文件层，旧的 ElementTree 统计读取器已移除。Pist 在读取后建立浏览用统计索引，不为每个列表条目重复扫描 XML。

实现中，文件会话位于 `berries.game.saves.files`，XML 文档工具与编解码位于 `berries.game.saves.codecs.xml`：`tree.py` 负责安全解析与节点保真，`progress.py`、`mods.py`、`session.py` 负责各自的游戏协议，`editing.py` 负责格式相关的输出预检和准备。业务层通过 codec 使用这些能力，不自行操作 XML 节点。

## 候选方案

| 方案 | 优点 | 对本项目的代价 |
| --- | --- | --- |
| `xml.etree.ElementTree` | 标准库、接口简洁、当前样本内存占用最低，适合只读统计 | 可配置保留注释和处理指令，但普通树不保留完整的命名空间声明上下文；仅在属性值中出现的 `ext:Type` 可能失去前缀声明，额外维护这套上下文增加复杂度 |
| `xml.dom.minidom` | 标准库、显式 DOM 节点、命名空间声明可作为属性保留，便于保留未知内容 | Python DOM 对象较多，当前样本解析、复制和序列化开销明显；真实大存档的通用 `deepcopy()` 触发递归深度错误，需要另选 DOM 原生复制或序列化往返 |
| `lxml.etree` | ElementTree 风格接口、可访问 `nsmap`、可保留 CDATA 和文档级注释／处理指令，当前样本解析和序列化最快 | 增加 libxml2 二进制依赖；开发检查另需 `types-lxml`；节点挂接会协调命名空间，不能直接假定复制保留所有 QName 语义；完整文档复制也需要专项回归 |
| `lxml.objectify` | 支持 Python 数值与 XML 的类型化读写 | 改变对象接口并可能引入类型标记，不能自动对应游戏的 .NET 类型和写出规则；现有字段校验已由 Pydantic 负责，不再引入第二套类型推断 |

标准库 ElementTree 的不足不是不能读取这些 XML，而是不足以直接承担“编辑后保留未知命名空间语义”的契约。lxml 也不是无条件无损：序列化格式可以改变，节点搬运仍需处理下述问题。

## 解析与编辑约束

解析保留空白、注释、处理指令、CDATA 和冗余命名空间声明，禁用实体展开、网络读取和外部 DTD 加载，并拒绝包含 DTD 的存档。不启用容错解析或 `huge_tree`，不为读入损坏数据而关闭解析器安全限制。字节输入遵循编码声明；已经解码的 `str` 使用 UTF-8 交给解析器并显式覆盖旧编码声明，覆盖 Collab 会话仍声明 UTF-16 的情况。配置含义见 [lxml 解析文档](https://lxml.de/parsing.html#parser-options)。

浮点数仍由 `str(value)` 转为字段文本，XML 库负责转义和文档编码，不模拟 .NET `Single` 的数值量化或部分格式规则。2026-10-20 起不承诺逐字段词法保真；例如修改 respawn 元组会统一编码 X、Y，不专门保留另一分量的小数或指数写法。字段值及未知扩展仍必须保留。

ElementTree 的 `tail` 表示节点之后、下一个节点之前的文本。删除出生点或收集品节点时保留这段文本，不能把它当作被删除节点的内容一起丢掉。

## 复制与命名空间

本机 lxml 6.1.3、libxml2 2.11.9 的回归发现，`deepcopy(ElementTree)` 会颠倒根节点之后多个注释／处理指令的顺序。内部需要复制完整 XML 时因此采用序列化重解析。该行为受回归测试约束，升级 lxml 后可以重新评估，不把原生复制始终正确作为前提。

当前文件对象遵循文件会话语义，明确不提供 `copy()` 或 `deepcopy()`；`SaveSlot` 仅是路径与编号位置，也不持有一组可复制文档。独立编辑复制 `vanilla`、`mods`、Campaign、Session 等领域对象；复制隔离其可写成员并保留域内别名，不复制文件流、提交基准或文件生命周期。领域对象保留的 XML 片段为不可变解码材料，不是第二棵可编辑节点树。

普通会话编辑修改独立领域对象，不在每次赋值时复制或修改 XML。提交时从保真输入建立候选 XML，只写变化字段，并完成 XML 字符、节点结构、ticks 精度和范围检查；主文件同身份双会话只联动改变的受支持字段，保留各自其他差异。全部编码成功后才进入文件提交；失败不写文件，也不声称回滚已编辑的内存对象。`copy_tree()` 用于编解码候选树与片段导入，不提供公开文档复制语义。

跨文档复制比同文档编辑更复杂。例如来源用 `xmlns:ext="urn:source"` 和 `type="ext:Special"`，目标用 `xmlns:other="urn:source"`；即使来源子树显式带有 `ext` 声明，lxml 挂接时也可能认为 URI 已存在而移除它，但不会改写属性值中的 `ext:Special`。仅复制 `nsmap` 或 `deepcopy()` 不能解决所有情况。

领域解码把已建模成员提取为普通对象，其输入片段带上完整的继承命名空间上下文；父级保真材料用内部唯一处理指令标记原位置，不再保留一份相同的可写状态。编码时以库生成的 XML 片段填入这些位置，跨文档导入同样采用片段替换后重解析，避免节点挂接改写 QName 上下文。这里不手拼用户数据或自行转义 XML，也不解析未知字段中的 QName；内部占位不进入最终结果。目标节点之后的文本仍归目标文档，来源的尾随文本不随快照导入。该保真策略有序列化和重解析成本，历史原语性能不能代表完整领域加载或写回性能。

## 本机性能对照

2026-10-17，在 Windows、CPython 3.14.7、lxml 6.1.3／libxml2 2.11.9 下，使用约 1.83 MB 的真实 `6.celeste`，预先读取字节，预热两次后测量七次取中位数。以下是后端原语对照，不含磁盘 I/O、字段校验或完整产品操作。

| 操作 | minidom | ElementTree | lxml |
| --- | ---: | ---: | ---: |
| 解析 | 188.79 ms | 23.27 ms | 15.48 ms |
| 树复制 | 299.57 ms | 40.28 ms | 21.87 ms |
| 序列化 | 74.91 ms | 62.15 ms | 11.61 ms |
| 解析并首次序列化 | 314.23 ms | 88.14 ms | 27.86 ms |
| 解析的进程私有内存增量 | 47.58 MiB | 10.02 MiB | 19.57 MiB |

minidom 的树复制测量使用 `cloneNode(True)`，ElementTree 和 lxml 使用 `deepcopy()`；lxml 这一行不是当前文件层保留文档顺序的复制实现。内存是三个独立子进程的增量中位数，受分配器影响，不是精确树对象大小。Mod 备份样本趋势一致；这些数据不证明所有 XML 或所有操作上 lxml 都更快。

本机诊断脚本和原始数据位于被忽略的 `.pist/scripts/probe_lxml_save_editing_20261017.py`、`.pist/benchmarks/lxml-save-editing-20261017.json`；实际文件层的独立测量位于 `.pist/scripts/verify_lxml_file_layer_20261017.py` 和 `.pist/benchmarks/lxml-file-layer-20261017.json`。诊断文件不是运行依赖，也不要求其他开发者拥有相同私人存档。

历史文件层测量包含当时的内部修改基准：主存档解析并建立基准为 26.66 ms，复制并保留修改基准为 38.99 ms，序列化为 11.83 ms；备份文件分别为 25.74 ms、37.51 ms、13.07 ms。当前已删除内部基准和初始化时的序列化，这组数据不代表当前解析和复制耗时；显式 XML 复制仍包含序列化往返，不等同于原语表中的 `deepcopy()`。

2026-10-18 另对同一树进行交替执行的直接对照，预热四次、正式测量各 21 次，排除文件读取和文件对象初始化：主文件 `deepcopy()` 为 27.22 ms、序列化重解析为 34.31 ms，增加 7.09 ms（约 26%）；备份分别为 19.96 ms 和 25.84 ms，增加 5.87 ms（约 29%）。原始数据为 `.pist/benchmarks/lxml-copy-20261018.json`。这项复制成本不应随每次普通字段编辑发生。

## 序列化差异与 .NET 回读

文档不提供 `modified`、diff 或确认流程。用户观察编辑差异只需分别取得修改前后的 `save.tostring()`，自行展示 diff，不需要知道底层格式或接触 lxml。独立验证 Berries 编解码正确性则属于开发测试：基准必须直接来自原始 XML，不能先经过领域模型重建；这类诊断可在前后使用 lxml C14N，统一属性顺序、空标签及重复命名空间声明，不清理可能被未知 QName 引用的前缀。两类对比目的不同，不能把开发验证步骤强加给日常调用。Berries 不恢复原 XML 声明、换行或空元素风格，不引入文本补丁或自定义 XML 序列化器。

2026-10-20 对本机 10 个真实主存档和 9 个 Mod 备份进行只读实验：不修改节点，直接通过 lxml 6.1.3／libxml2 2.11.9 解析并序列化。19 个文件忽略声明引号、CRLF/LF 和空元素结束前空格后，文本均完全一致。额外的 Hyperline 配置存在成对空标签变为自闭合的差异；此结果不代表任意 XML 都能恢复原始文本。副本和统计位于 `.pist/benchmarks/lxml-roundtrip-20261020/`，真实存档未写回。

同日另将这 19 个真实文件通过当前 Berries 领域读写链生成内存副本。普通 `tostring()` 比较发现重组片段会重复带入继承的命名空间声明，并非最小文本变化；前后均使用 lxml C14N 后，19 个文件完全一致。该结果支持当前样本的无编辑往返，不证明所有输入或实际游戏加载都正确。未清理未知命名空间，也未写回真实文件；原始普通 diff 位于 `.pist/benchmarks/save-domain-roundtrip-20261020/`。

```python
from difflib import unified_diff
from berries.game.saves.files.main import MainSave

save = MainSave.read(path)
before = save.tostring()
save.deaths += 1
after = save.tostring()
print(''.join(unified_diff(before.splitlines(True), after.splitlines(True))))
# 是否保存、保存到哪里，由调用方另行决定。
```

合成样本完成了“.NET 生成 → Python 未编辑／编辑／还原并写出 → .NET XmlSerializer 回读”的 30 项验证，覆盖 UTF-8／UTF-16、CRLF／LF、缩进／紧凑形式、空字符串、`null`、文本空白和小数坐标，字段值符合预期。替换后使用实际文件层重新运行。验证环境为 .NET 10.0.11，不等价于已用所有游戏运行时验证，也没有写回真实游戏存档或启动游戏加载。

版本控制中的专项测试覆盖命名空间同前缀不同 URI、同 URI 不同前缀、嵌套重绑定、未知 QName、CDATA、文档级注释／处理指令顺序、Unicode 编码声明、宽树复制、编辑失败隔离和只写入变化字段。更换 XML 后端或升级相关行为时应继续运行这些回归。
