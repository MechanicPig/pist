# Pist 开发与审查

仅在新增或修改外部解析、Pydantic 模型、SQLite 或规则 schema、CLI/浏览器协议、跨模块重构，或用户明确要求代码 review 时使用。纯文案、TCSS 微调、格式化和已验证局部行为的机械修复无需读取。

先阅读项目根目录 `AGENTS.md`，再仅打开当前改动涉及的模块、调用方和测试。目标是让实现的职责、数据流和错误边界清晰，而不是为了形式统一而重排代码。

## 设计与重构

- 先识别稳定职责。游戏文件、存档、Mod 与地图读取归 `game`；Pist 对地图实体和入口的可配置解释归 `entities`、`map_entrances`；UI 只协调交互和领域服务。不要让 UI 解析 XML/YAML/SQLite，也不要让领域层依赖 Textual 或浏览器。
- 新能力若使一个活动模块混入新的稳定职责、让 `__init__.py` 承担实现，或使浏览器请求和响应两端难以同步，应在同一改动中拆分；否则说明暂不拆分的具体边界。
- 名称应描述实际语义和适用范围。不要以过宽名称暗示通用能力，例如只针对统计归属类别的查询不应命名为一般性的 `has_kind`。集合、规则和记录倾向复数；单一模型、协议和过程倾向单数，但不为表面一致性重命名。
- 能用结构化值模型表达身份时，不以控制字符拼接字符串作为长期键。序列化边界可以编码为字符串，但应保持独立的解析与按值匹配语义。
- 需求调整为由新配置、规则或模型表达后，立即审计旧的派生字段、统计逻辑和调用链。确认新来源已覆盖原职责时，在同一改动中删除旧实现与测试，避免两个真相来源随时间分歧。
- 内部开发的本地 schema 或路径已升级时，直接迁移现有开发数据并删除旧兼容分支；不要留下双读、旧字段或一次性迁移代码。
- 新增或修改路径、SID、Dialog key、扩展名等外部标识的比较、去重或派生前，先阅读 `docs/path-identity-semantics.md`。根据对应实现和平台证据区分物理路径、虚拟资源路径与标识字符串；不得把 `Path`、`PurePosixPath` 或 `casefold()` 的默认行为当作身份语义。

## 边界、数据与错误

- XML、YAML、JSON、HTTP 响应、SQLite 记录和浏览器请求均是外部边界：先以 Pydantic 或等价的结构校验转换为精确内部模型，再进入领域逻辑。不要在深层业务代码中散落手工字典检查。
- 解析器不需要的 YAML 自动类型推断应关闭；若来源语义是字符串，使用保留原始标量的 loader，再由模型校验。例如 SID、版本、名称和会话文本不能因 `01`、`true` 或日期样式而改变。
- 边界错误必须转换为调用方约定的可诊断异常类型；不要让 `TypeError`、`KeyError` 等实现细节绕过 UI 或 CLI 的既有错误提示。
- 不丢失原始语义差异：属性未写入不同于显式默认值；规则未知不同于明确排除；不可确认的收集品不得自动计入统计。
- 外部事实模型优先不可变；只有确有累积或编辑职责的状态才可变。共享常量映射在确需运行时防改时使用只读容器；函数参数和返回值则用接口类型表达调用契约。

## 类型与实现表达

- 类型注解服务于接口和意图，不为通过检查而罗列偶然实现。容器只需承载组件时用 `Widget`；确实承诺具体模型或需要区分分支时才保留具体类型。局部字面量能可靠推导时不补冗余注解。
- 三个及以上稳定相关字段考虑 dataclass/Pydantic 模型；三种及以上反复出现的值类型考虑 type alias。反之，不为很小的局部数据增加模型。
- 函数内反复构造、只按固定键查值的映射提取为模块常量；带类型判断、资源构造、局部状态或错误恢复的 `match` 保留为控制流。不要为了消灭 `match` 而削弱类型表达。
- 迭代消费者不需要随机访问或重复遍历时，优先生成器，避免为返回 tuple/list 进行无必要的聚集和复制。

## 性能、资源与 UI

- 浏览和启动路径不应无条件解析全部地图 `.bin`；按需读取。可复用但昂贵的扫描结果可持久化缓存，并以 Mod 文件或目录变化作为失效条件。
- 长操作保持 UI 可响应：在协程中分步更新确定的进度；不要先展示未排序内容再替换列表，造成误操作风险。
- ZIP、文件流和 loopback HTTP 服务应在使用后关闭，避免阻塞 Loenn 或游戏。
- 浏览器地图预览的 JSON 状态、操作请求和静态前端必须成对修改；协议测试覆盖字段和行为，不以中文 UI 文案的逐字匹配替代功能测试。

## 代码审查

进行仓库级审查、用户指定维度的专项 review，或需要系统评价 dead code、性能、类型、组织、测试与 import 时，完整阅读并使用 [代码审查判定原则](references/code-review.md)。普通实现后的轻量 review 不必加载完整清单，但仍检查真实功能分支、职责边界、旧逻辑清理、类型、资源、重复计算和测试契约。

## 实现与 review 检查

新增或实质改变一项完整能力后，自动进行一次轻量 review；纯局部缺陷修复、文案、样式和机械重命名无需触发。以下变化视为完整能力：新增或改变用户工作流、CLI 行为或 UI 阻断；规则语义、数据模型、SQLite 持久化或配置格式；外部输入解析、存档/地图读取、网络或浏览器协议；跨两个及以上稳定模块传递的新状态或回调；缓存、并发、后台任务或可能影响性能的批处理。Review 固定检查功能分支（正常、缺失、冲突与刷新后的状态）、职责边界与旧逻辑清理，以及类型、资源、重复计算和测试是否对应真实行为。

1. 明确输入边界、领域结果、调用方及失败时的用户可见行为。
2. 检查新代码是否复用已有模型、规则和服务，而非复制解析或统计逻辑。
3. 专项 review 按参考文档检查全部指定维度；对没有发现问题的维度也明确记录已检查，而不是用测试通过代替审查。
4. 覆盖每个独立条件：特别是布尔收集状态、缺失/显式值、冲突和无数据路径；测试断言行为与数据契约，而非偶然的布局或文案。
5. 按影响面运行相关测试；跨层、持久化、解析或协议变更再运行完整 pytest、Ruff 和 Pyright。
6. 交付前检查是否新增了不必要的兼容层、重复扫描、未关闭资源或未同步的协议端。
