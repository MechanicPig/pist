# Pist 开发与审查

新增或修改描述中的能力时使用；纯文案、格式化、TCSS 外观微调和已验证局部行为的机械修复无需加载。改变布局可达性、焦点、拖动或取消行为不属于纯外观微调。

## 工作流程与参考选择

1. 先阅读项目根目录 `AGENTS.md`，检查工作区，再追踪当前任务的入口、调用方、实现与测试；不为形式统一而重排代码。
2. 明确输入、结果、持久化状态和失败行为；涉及外部协议时核对文档与真实样本，不能仅凭现有 mock 推断语义。
3. 根据下表完整读取适用的参考文档；跨领域任务读取相关各份，不加载无关业务清单。
4. 实施后按影响面验证，并完成下文要求的轻量或专项审查；交付说明行为变化、验证结果及仍未证实的部分。

## 设计与重构

- 先识别稳定职责。游戏文件、存档、Mod 与地图读取，以及存档的内存编辑与编解码归 `berries.game`；存档一次性 `read()`，显式 `write()`，内容输入输出使用 `fromstring()`／`tostring()`；通用路径及文本／二进制流适配复用 `TextDocMixin`，不保留文件会话或关闭提交语义，备份由调用方自行使用文件工具处理，不提供备份 API。公共实体和入口解释归 `berries.entities`、`berries.map_entrances`，个人统计与审计归 Pist 对应领域；UI 只协调交互和领域服务。不要让 UI 解析 XML/YAML/SQLite，也不要让领域层依赖 Textual 或浏览器。
- 提取公共能力时区分平台事实、通用机制与应用策略，并追踪默认参数、回退顺序、排序、格式化、缓存键及诊断输出，不能只移动文件或移除 UI 导入。公共层保留可供调用方决策的事实与机制；语言偏好、个人展示和继续策略由应用显式组合。共享机制应覆盖真实的共同语义，例如任意 Dialog key 的语言选择，而不是按当前调用页面复制多个窄接口；额外行为仍需需求或平台证据，不因“通用”就自动增加。
- 按状态与不变量归属选择方法位置：由一个对象自身数据决定的查询、匹配或派生值，考虑放到该类型；方法不使用接收者状态、只转发另一个对象的属性时，检查是否应删除包装或迁到真正的拥有者。不要反向要求所有 free function 类化，Path-like 值类型、跨对象操作和应用策略仍按各自契约组织。
- 继承须表达可替代的领域关系，而非只为复用代码、添加诊断或迁就旧调用。基类不默认承担某个子类的专属语义；兄弟角色不因字段相似建成父子类。调用方频繁“接受父类但排除某子类”、靠标志或冗余枚举恢复类型时，重新检查模型；加载上下文、附加结果及服务集合优先评估组合，不用属性转发伪装成被组合对象。
- 从实际调用方式设计最小充分接口：仅需路径或 key 时不要求完整模型，正常对象无需接受无业务含义的 None；完整加载入口应协调自身必需步骤，只有调用方确实拥有预先加载结果时才支持显式复用。UI 接收准备好的领域数据与服务，加载和组装由外部入口负责，不靠 UI 构造过程隐式补齐依赖。
- 新能力若使一个活动模块混入新的稳定职责、让 `__init__.py` 承担实现，或使浏览器请求和响应两端难以同步，应在同一改动中拆分；否则说明暂不拆分的具体边界。
- 名称应描述实际语义和适用范围。不要以过宽名称暗示通用能力，例如只针对统计归属类别的查询不应命名为一般性的 `has_kind`。集合、规则和记录倾向复数；单一模型、协议和过程倾向单数，但不为表面一致性重命名。
- 能用结构化值模型表达身份时，不以控制字符拼接字符串作为长期键。序列化边界可以编码为字符串，但应保持独立的解析与按值匹配语义。
- 需求调整为由新配置、规则或模型表达后，立即审计旧的派生字段、统计逻辑和调用链。确认新来源已覆盖原职责时，在同一改动中删除旧实现与测试，避免两个真相来源随时间分歧。检查不能止于刚修改的符号：继续追踪调用方参数、反向索引、类型判别、特殊重写和相邻包装，删除因新模型而失去职责的间接访问，不给旧容器留下只为维持接口的查询方法。
- 内部开发的本地 schema 或路径已升级时，直接迁移现有开发数据并删除旧兼容分支；不要留下双读、旧字段或一次性迁移代码。
- 新增或修改路径、SID、Dialog key、扩展名等外部标识的比较、去重或派生前，先阅读 `docs/path-identity-semantics.md`。根据对应实现和平台证据区分物理路径、虚拟资源路径与标识字符串；不得把 `Path`、`PurePosixPath` 或 `casefold()` 的默认行为当作身份语义。

## 边界、数据与错误

- XML、YAML、JSON、HTTP 响应、SQLite 记录和浏览器请求均是外部边界：先以 Pydantic 或等价的结构校验转换为精确内部模型，再进入领域逻辑。不要在深层业务代码中散落手工字典检查。
- 解析器不需要的 YAML 自动类型推断应关闭；若来源语义是字符串，使用保留原始标量的 loader，再由模型校验。例如 SID、版本、名称和会话文本不能因 `01`、`true` 或日期样式而改变。
- 边界错误必须转换为调用方约定的可诊断异常类型；不要让 `TypeError`、`KeyError` 等实现细节绕过 UI 或 CLI 的既有错误提示。
- 区分“读取失败如何继续”与“已读事实需要怎样提示”：前者可用携带来源、阶段和原因的异常及 on_error 回调，后者可用结构化问题或结果。回调、返回值和 warning 各有适用场景，不在同一失败链上重复收集再捕获；明确默认是否抛出、回调返回或抛出的效果，以及部分结果与已有诊断的归属。应用负责面向用户的文案，不让公共结果依赖调用页面的称谓。
- 不丢失原始语义差异：属性未写入不同于显式默认值；规则未知不同于明确排除；不可确认的收集品不得自动计入统计。
- 外部事实模型优先不可变；只有确有累积或编辑职责的状态才可变。共享常量映射在确需运行时防改时使用只读容器；函数参数和返回值则用接口类型表达调用契约。
- 诊断信息应包含操作、目标、失败阶段和原因，区分明确失败、已完成与结果不确定。按恢复需要保留必要上下文，让临时气泡消失后仍能查到可行动信息；不要输出凭证、完整敏感响应或为普通错误无条件保存大快照。
- 增加回读、重试、锁或额外校验前，说明它防范的具体风险、协议证据、恢复方式和额外成本；不能只因“更保守”就增加网络往返或阻断。明确何种证据足以确认成功，以及何种不确定状态必须保留。

## 类型与实现表达

- 类型注解服务于接口和意图，不为通过检查而罗列偶然实现。容器只需承载组件时用 `Widget`；确实承诺具体模型或需要区分分支时才保留具体类型。容器初始化沿用 AGENTS.md 的变量注解与字面量／普通构造器规则，不为静态提示引入运行时泛型别名；非空初始化能可靠推导出所需类型时不补冗余注解，已声明属性的后续赋值不重复标注，实际依赖运行时类型实参的类型保留其构造契约。
- 内部对象优先使用直接构造和既有 Python 协议；只有解析、替代来源或其他独立语义才增加工厂。廉价、确定的派生值可用 property，不保存可与来源矛盾的副本；需要创建整批对象或读取外部资源的 property 须明确成本与生命周期。实例注解靠近初始化，class-scope 注解保留给模型字段、类变量或确需声明的契约；标准缓存设施仅在失效条件明确时替代手工缓存状态。
- 三个及以上稳定相关字段考虑 dataclass/Pydantic 模型；三种及以上反复出现的值类型考虑 type alias。反之，不为很小的局部数据增加模型。
- 函数内反复构造、只按固定键查值的映射提取为模块常量；带类型判断、资源构造、局部状态或错误恢复的 `match` 保留为控制流。不要为了消灭 `match` 而削弱类型表达。
- 迭代消费者不需要随机访问或重复遍历时，优先生成器，避免为返回 tuple/list 进行无必要的聚集和复制。

## 性能、缓存与资源

- 浏览和启动路径不应无条件解析全部地图 `.bin`；按需读取。可复用但昂贵的扫描结果可持久化缓存，并以 Mod 文件或目录变化作为失效条件。
- 长操作保持 UI 可响应：在协程中分步更新确定的进度；不要先展示未排序内容再替换列表，造成误操作风险。
- 单值查询不应默认先生成全量结果再筛选，例如查询一种语言时先构造所有翻译、获取一个来源时重建一批地图对象。共用规则不等于复用最重的聚集路径；拆出共享查找语义并让单值和批量入口各取所需，不把无意义分配仅以“开销不大”保留下来，也不夸大为实测性能瓶颈。
- ZIP、文件流和 loopback HTTP 服务应在使用后关闭，避免阻塞 Loenn 或游戏。
- 网络优化先画出一次用户操作的请求链，计数定位、字段、内容、写入、恢复等请求及串行阶段；同时估算分页、批量和未知选项随规模增长的成本。独立读取可并发，兼容的操作可批量，连接在明确生命周期内复用，但不能跳过冲突检查或扩大写入权限。
- 缓存须明确键与隔离范围、有效期、失效和清除方式、未命中结果是否缓存、失败是否缓存、并发访问及资源退出行为。展示或候选缓存不等于实时事实，不能替代写入前核对。
- 性能结论使用同一目标与工作量的前后 benchmark，记录环境、样本量和请求数，区分冷启动／热缓存、网络等待／本地计算。profile 用于定位，benchmark 用于计时，分开运行；遵循 `AGENTS.md` 的低开销 profiler 约定，不把插桩耗时当作收益。少量在线样本只能支持有限结论，不将网络波动归功于优化。

## 并发、取消与交互

- 先界定任务所有者与取消范围：关闭编辑、取消等待、撤销排队和回滚持久化不是同一操作。不要用框架的排他任务默认行为代替业务策略；新交互不能隐式取消已接受的写入。
- 对正常结束、异常、取消和进程中断分别说明已持久化内容、远端是否可能生效、后续恢复与可否重试。等待者取消不应自动等同于底层任务取消；不可回滚的外部请求不能描述为已撤销。
- 后台任务与前台编辑、人工确认、刷新及退出的关系须明确；进度只报告确定完成的阶段，不以旧状态计入本次成功。更新列表时保留稳定身份、焦点和选择，不无必要地清空重建。
- 框架已提供主题、菜单或其他状态切换入口时，先检查内置入口和可观察状态，再决定是否自建操作。持久化应监听真正的状态变化而不只监听自定义按钮，避免两条入口行为分叉；启动恢复与用户修改要区分，不能仅恢复设置就触发写回。
- 交互验证使用用户真实输入路径：按钮直接调用 `.press()` 或控件存在不能证明鼠标可点、布局可见或焦点可达。按风险覆盖窄窗口、滚动、键盘／鼠标、取消与重开；布局、焦点或浏览器预览变更仍按 `AGENTS.md` 人工验证。

## 测试与在线验证

- 协议测试分别表示查询响应、写入响应和实际存储结果，覆盖缺失、空值、归一化及部分成功等真实差异；不能只把本地编码值原样回填为远端响应。对已确认的请求预算，可测试可观测请求数上界与规模增长，而非偶然的私有调用过程。
- 在线写入只在明确的专用合成测试目标内执行，先核验目标身份并隔离本地数据库；记录本次创建的精确远端 ID，清理仅限这些 ID。无法确认新增结果时保留诊断并核查，不凭名称猜测删除，不触碰正式记录。
- 在线测试的独立回读用于验证协议及实际保存结果，不据此默认给产品每次操作增加回读。无法在线或人工验证时，明确离线测试仍未证明的部分。

## 代码审查与交付

进行仓库级审查、用户指定维度的专项 review，或需要系统评价功能实现、代码质量、代码组织与测试时，完整阅读并使用 [代码审查判定原则](references/code-review.md)。审查和报告固定按这四类组织；dead code、性能、边界建模、类型、Pydantic、命名和 import 属于代码质量，职责边界、目录结构、公共入口、god module 与旧实现清理属于代码组织。普通实现后的轻量 review 不必加载完整清单，但四类都应经过判断，不以测试通过代替功能和代码审查。

接口审查先从真实入口还原普通调用、定制策略和失败传播的最小用法，再逐项追踪参数与包装字段的来源、消费及阶段语义；不能只围绕现有签名检查实现是否正确。具体检查方法见上述参考的“接口与对象建模”。

新增或实质改变一项完整能力后，自动进行一次轻量 review；纯局部缺陷修复、文案、样式和机械重命名无需触发。以下变化视为完整能力：新增或改变用户工作流、CLI 行为或 UI 阻断；规则语义、数据模型、SQLite 持久化或配置格式；外部输入解析、存档/地图读取、网络或浏览器协议；跨两个及以上稳定模块传递的新状态或回调；缓存、并发、后台任务或可能影响性能的批处理。轻量 review 同样按功能实现、代码质量、代码组织和测试四类检查，但只展开与改动风险相关的要点。

1. 功能实现：明确输入边界、领域结果、调用方及失败时的用户可见行为，覆盖正常、缺失、无效、冲突、刷新和持久化后的状态。
2. 代码质量：检查是否复用已有模型、规则和服务，并检查 dead code、类型、资源、重复计算、边界解析、命名与 import。
3. 代码组织：检查职责和依赖方向、公共入口、旧逻辑清理，以及新增能力是否使模块形成新的稳定职责或 god module。
4. 测试：确认测试覆盖真实行为与数据契约，而非偶然的调用次数、内部容器、布局或文案；修复夹具时不得无意删除另一条覆盖。
5. 专项 review 按参考文档检查全部指定维度；四类中没有发现问题的类别也明确记录已检查，而不是用测试通过代替审查。
6. 按 `AGENTS.md` 的“修改与验证规则”选择验证范围；纯机械调整不因跨模块、跨层或跨包而重复运行全量测试。
