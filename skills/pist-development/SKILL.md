# Pist 开发与审查

仅在新增或修改外部解析、Pydantic 模型、SQLite 或规则 schema、CLI/浏览器协议、跨模块重构，或用户明确要求代码 review 时使用。纯文案、TCSS 微调、格式化和已验证局部行为的机械修复无需读取。

先阅读项目根目录 `AGENTS.md`，再仅打开当前改动涉及的模块、调用方和测试。目标是让实现的职责、数据流和错误边界清晰，而不是为了形式统一而重排代码。

## 设计与重构

- 先识别稳定职责。游戏文件、存档、Mod 与地图读取归 `game`；Pist 对地图实体和入口的可配置解释归 `entities`、`map_entrances`；UI 只协调交互和领域服务。不要让 UI 解析 XML/YAML/SQLite，也不要让领域层依赖 Textual 或浏览器。
- 新能力若使一个活动模块混入新的稳定职责、让 `__init__.py` 承担实现，或使浏览器请求和响应两端难以同步，应在同一改动中拆分；否则说明暂不拆分的具体边界。
- 名称应描述实际语义和适用范围。不要以过宽名称暗示通用能力，例如只针对统计归属类别的查询不应命名为一般性的 `has_kind`。集合、规则和记录倾向复数；单一模型、协议和过程倾向单数，但不为表面一致性重命名。
- 能用结构化值模型表达身份时，不以控制字符拼接字符串作为长期键。序列化边界可以编码为字符串，但应保持独立的解析与按值匹配语义。
- 需求调整为由新配置、规则或模型表达后，立即审计旧的派生字段、统计逻辑和调用链。确认新来源已覆盖原职责时，在同一改动中删除旧实现与测试，避免两个真相来源随时间分歧。
- 内部开发的本地 schema 或路径已升级时，直接迁移现有开发数据并删除旧兼容分支；不要留下双读、旧字段或一次性迁移代码。
- 新增或修改路径、SID、Dialog key、扩展名等外部标识的比较、去重或派生前，先阅读 `docs/path-identity-semantics.md`。根据对应实现和平台证据区分物理路径、虚拟资源路径与标识字符串；不得把 `Path`、`PurePosixPath` 或 `casefold()` 的默认行为当作身份语义。

## 边界、数据与错误

- XML、YAML、JSON、HTTP 响应、SQLite 记录和浏览器请求均是外部边界：先以 Pydantic 或等价的结构校验转换为精确内部模型，再进入领域逻辑。不要在深层业务代码中散落手工字典检查。
- 解析器不需要的 YAML 自动类型推断应关闭；若来源语义是字符串，使用保留原始标量的 loader，再由模型校验。例如 SID、版本、名称和会话文本不能因 `01`、`true` 或日期样式而改变。
- 边界错误必须转换为调用方约定的可诊断异常类型；不要让 `TypeError`、`KeyError` 等实现细节绕过 UI 或 CLI 的既有错误提示。
- BinaryPacker 的解析、跳过和树遍历不得依赖 Python 调用栈容量；按声明的嵌套与元素数量限制处理，并以 `BadMapBin` 报告越界或截断。深度默认限制为 32 层（包含根节点），优先使用解析函数的 `max_depth`，其次使用 `BERRIES_MAX_MAP_DEPTH`；配置须为正整数。元数据的显式提前返回仍不验证未读取的后续 payload。
- 不丢失原始语义差异：属性未写入不同于显式默认值；规则未知不同于明确排除；不可确认的收集品不得自动计入统计。
- 全收集判定须核对当前规则确认的红莓、月莓实例 ID，不以存档收集总数抵消缺失实例；无法确认 ID 或所需实例的 ID 在实际地图实体中重复时不得自动判定全收集。重复检查不限于单个类别，也须考虑未知或不参与统计的实体；单个实体被多个统计规则投影不等于多个实体重复。记录编辑发现重复 ID 时，须通过运行时警告展示地图与异常 ID，不得只静默改变完成状态。
- 类别重命名、删除涉及规则文件与审计引用时，先准备全部候选文件与旧文件副本，再协调数据库事务；失败恢复旧文件，恢复失败保留副本并报告位置。仅在提交成功后更新 UI 内存；不要将这种恢复机制描述为跨介质的崩溃原子事务。
- 外部事实模型优先不可变；只有确有累积或编辑职责的状态才可变。共享常量映射在确需运行时防改时使用只读容器；函数参数和返回值则用接口类型表达调用契约。

## 类型与实现表达

- 类型注解服务于接口和意图，不为通过检查而罗列偶然实现。容器只需承载组件时用 `Widget`；确实承诺具体模型或需要区分分支时才保留具体类型。局部字面量能可靠推导时不补冗余注解。
- 三个及以上稳定相关字段考虑 dataclass/Pydantic 模型；三种及以上反复出现的值类型考虑 type alias。反之，不为很小的局部数据增加模型。
- 函数内反复构造、只按固定键查值的映射提取为模块常量；带类型判断、资源构造、局部状态或错误恢复的 `match` 保留为控制流。不要为了消灭 `match` 而削弱类型表达。
- 迭代消费者不需要随机访问或重复遍历时，优先生成器，避免为返回 tuple/list 进行无必要的聚集和复制。

## 性能、资源与 UI

- 浏览和启动路径不应无条件解析全部地图 `.bin`；按需读取。可复用但昂贵的扫描结果可持久化缓存，并以 Mod 文件或目录变化作为失效条件。
- 长操作保持 UI 可响应：在协程中分步更新确定的进度；不要先展示未排序内容再替换列表，造成误操作风险。
- ZIP、文件流和 loopback HTTP 服务应在使用后关闭，避免阻塞 Loenn 或游戏。
- 体验记录写入工作流共用 `pist.records.lock.record_writer_lock`，以同一数据目录的跨进程排他锁防止并发覆盖；新入口须在读取编辑快照前获取，并保持至工作流退出。此约束不保护直接存储调用；需要并行编辑时另行设计记录级冲突检查。测试使用隔离的数据目录，并覆盖正常退出、异常和进程终止后的释放。
- UI 与 CLI 的记录同步统一经由 `RecordSyncService`，不得直接按地图名选择远端行或提供跳过核对的写入旁路。首次新增先持久化尝试，获得远端 ID 后原子保存关联并解除尝试；不确定的新增不能因名称变化、重启或网络恢复而自动重试。
- 已关联记录核对时，远端相对基准的变化若已与本地待写值一致，该字段不构成冲突，不掩盖其他字段的真实冲突。重新核对后，所有待写字段均与远端一致时直接确认并刷新基准，不为推进同步状态重复写入；读取快照本身不推进确认基准。批量同步沿用单条同步的冲突与恢复交互，取消或失败时停止后续记录，保留已完成结果。
- 单条已关联记录按远端记录 ID 查询核对和回读；批量同步共享首次完整表格读取，不对每条一致记录重复请求，已有记录按批次 ID 重新核对、提交并立即回读确认。未绑定记录匹配与不确定新增恢复仍读取完整表格，局部查询不得替代用于匹配的完整快照。人工交互后废弃旧快照；排队、已提交和已确认明确区分，失败不自动重试，未确认结果保持待同步。测试覆盖大量实际更新与后续批次失败时前批确认结果的保留，而非仅覆盖大量一致记录。
- 体验记录的起始日期、结束日期与 Mod 更新时间统一使用纯日期，表格时间戳按系统本地时区解释后提取日期，写出时编码为该日期的本地零点；日期选择器默认值、地图更新时间的日期提取和记录创建日期的显示同样使用本地时间，但创建时间戳仍以 UTC 保存。不得硬编码 UTC 或 UTC+8，也不得用当前时区偏移代替目标日期的本地时区规则。复选框在表格读取边界将空值解码为 `False`，本地磁带字段统一为默认 `False` 的非空布尔值，不保留未知状态或比较层特判。边界测试须包含与本地编码不同的真实远端表示及跨 UTC 日期边界的时间戳，避免直接回填编码结果掩盖读写不对称。
- 不确定新增的候选按发起请求时保存的地图名与 Mod 元数据名匹配，排除已经关联的远端 ID；只有用户明确选择且重新读取后仍有效的候选才能绑定，绑定本身不确认同步。没有候选不等于新增失败；解除保护须单独确认请求已结束且远端未新增，并再次读取检查。
- 浏览器地图预览的 JSON 状态、操作请求和静态前端必须成对修改；协议测试覆盖字段和行为，不以中文 UI 文案的逐字匹配替代功能测试。
- 路线保存先持久化候选结果，成功后才更新页面保存基准；写入失败须返回 JSON 错误，并保持取消操作和重新打开时的原保存结果。

## 代码审查

进行仓库级审查、用户指定维度的专项 review，或需要系统评价功能实现、代码质量、代码组织与测试时，完整阅读并使用 [代码审查判定原则](references/code-review.md)。审查和报告固定按这四类组织；dead code、性能、边界建模、类型、Pydantic、命名和 import 属于代码质量，职责边界、目录结构、公共入口、god module 与旧实现清理属于代码组织。普通实现后的轻量 review 不必加载完整清单，但四类都应经过判断，不以测试通过代替功能和代码审查。

## 实现与 review 检查

新增或实质改变一项完整能力后，自动进行一次轻量 review；纯局部缺陷修复、文案、样式和机械重命名无需触发。以下变化视为完整能力：新增或改变用户工作流、CLI 行为或 UI 阻断；规则语义、数据模型、SQLite 持久化或配置格式；外部输入解析、存档/地图读取、网络或浏览器协议；跨两个及以上稳定模块传递的新状态或回调；缓存、并发、后台任务或可能影响性能的批处理。轻量 review 同样按功能实现、代码质量、代码组织和测试四类检查，但只展开与改动风险相关的要点。

1. 功能实现：明确输入边界、领域结果、调用方及失败时的用户可见行为，覆盖正常、缺失、无效、冲突、刷新和持久化后的状态。
2. 代码质量：检查是否复用已有模型、规则和服务，并检查 dead code、类型、资源、重复计算、边界解析、命名与 import。
3. 代码组织：检查职责和依赖方向、公共入口、旧逻辑清理，以及新增能力是否使模块形成新的稳定职责或 god module。
4. 测试：确认测试覆盖真实行为与数据契约，而非偶然的调用次数、内部容器、布局或文案；修复夹具时不得无意删除另一条覆盖。
5. 专项 review 按参考文档检查全部指定维度；四类中没有发现问题的类别也明确记录已检查，而不是用测试通过代替审查。
6. 按影响面运行相关测试；跨层、持久化、解析或协议变更再运行完整 pytest、Ruff 和 Pyright。
