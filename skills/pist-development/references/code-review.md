# 代码审查判定原则

先追踪真实入口、调用链、框架注册、外部语义和数据规模，再报告有证据的问题；不要把个人风格偏好写成 finding。非归档代码是默认审查范围，`archive` 只检查“活动代码不得依赖它”的边界。

## 功能实现

- 从用户需求和真实入口追踪完整数据流，确认输入、领域转换、持久化、输出及用户可见结果彼此一致；测试通过不能代替对实现分支的检查。
- 分别检查正常、缺失、无效、冲突、取消、刷新和重载后的状态；只检查顺利路径不足以证明功能完成。不存在某种状态时不机械补分支，但应有代码或协议证据。
- 对 XML、YAML、JSON、HTTP、SQLite、游戏文件和第三方工具数据，先核对真实协议语义；测试夹具或开发 Agent 的假设不能单独证明行为正确。证据不足时明确建议针对真实数据复查。
- 边界错误应转换为调用方约定的可诊断异常，并到达既有 UI、CLI 或报告通道；不要让 `TypeError`、`KeyError` 等实现细节绕过用户可见错误处理。
- 不丢失原始语义差异：属性未写入不同于显式默认值，规则未知不同于明确排除，不可确认的收集品不得自动计入统计。
- 浏览器或其他双端协议的请求、响应、静态前端和 Python 端必须同步；持久化工作流还要检查写入成功、部分失败、重试、重启和重新读取后的状态。

## 代码质量

### Dead code

- 从产品入口、稳定公共接口、框架注册、序列化或反射入口均不可达，只被测试调用的实现，视为 dead-code 候选；测试不能单独证明产品用途。
- 一组函数、类、字段或方法即使彼此引用，若整组没有外部可达入口，仍属于不可达代码。同步检查只写不读的字段、只供 dead code 使用的导入、常量、适配层和测试。
- 不机械删除为了补全值类型、协议或公共模型语义而保留的对称方法或属性。保留应有清晰的公共契约、协议关系或可预期用途，而不是仅以“以后可能会用”解释。
- Textual 事件、Pydantic 字段、CLI 注册、回调、插件和动态导入可能没有普通文本调用点；确认框架入口后再判定。

### 性能与资源

- 查找循环、排序、过滤、SQL 行处理和 UI 刷新中的无条件重复计算、复制和分配；尤其注意 `setdefault` 默认实参提前求值、重复 materialize、同一数据反复序列化或解析，以及缓存命中仍执行原计算。
- 区分固定小对象的微小开销与随地图、实体、occurrence 或文件大小增长的工作。完全不必要但影响较小的重复分配可以报告为低优先级，不夸大为用户可感知性能问题。
- 大量数据只需流式消费、投影、去重或聚合时，避免先复制为完整容器；能在 SQLite 查询、生成器或已有索引中完成的工作，不先搬到 Python 再处理。
- 对明显更优的复杂度给出数据规模和替代结构，例如重复线性查找改为集合或映射、逐项全表查询改为批量查询。不存在合理规模收益时，不以大 O 形式差异单独立项。
- 检查 ZIP、文件流、数据库连接、后台任务和 loopback HTTP 服务的生命周期；性能优化不能以泄漏资源、破坏失效条件或缓存错误结果为代价。

### 边界、类型与模型

- 对字段集合确定的 XML、YAML、JSON、HTTP、SQLite 等外部输入，优先由 Pydantic 或明确的边界模型一次性校验、转换并保留字段路径；不要在业务层散落 `dict.get`、类型判断、逐字段 `int(...)` 和重复错误包装。
- 对字段集合确定的结构化输出，优先使用模型序列化、标准库或既有格式库；不要手工拼接 JSON、TOML、查询参数或协议字段。面向人的短文本和确有版式语义的渲染不在此限。
- 除 argparse 组装代码外，函数和方法边界、类字段、跨模块容器及无法可靠推导的局部值应基本被类型覆盖；不要求给显而易见的局部变量重复标注。
- 注解必须反映调用者可依赖的能力、可变性、缺失状态和返回契约。检查过宽的 `Any` 或 `object`、偶然实现联合、错误的具体控件类型，以及标注存在但与运行时值或语义错位的情况。
- Pydantic 模型应使用字段类型、`Annotated`、`Field`、`annotated_types` 约束、枚举和模型配置表达可声明约束；只有跨字段关系、上下文依赖或格式库无法表达的规则才保留手工 validator。
- 外部输入的转换尽量放入拥有该字段语义的值类型或模型，使 XML、YAML、JSON 等入口复用同一契约；同时避免为了统一形式给已经类型安全的内部调用增加无意义包装。

### Python 表达、命名与 Import

- 识别违背 Python 数据模型和惯用接口、导致额外状态或分支的实现，而不是笼统追求“更 Pythonic”。例如已有迭代、上下文管理、排序键、映射方法或标准协议可直接表达时，不手写等价控制流。
- 名称应清晰、简明并与实际语义范围一致。社区已形成稳定共识的缩写（如 `id`、`url`、`db`、`num`、`dir`、`attr`、`req`、`resp`）可以使用；复合类名已经很长时，也应考虑缩写，而不只缩写局部变量。
- 检查 magic number：协议编号、状态码、单位换算和业务阈值等语义不直观的数字，应优先复用或定义有语义名称的枚举、常量或值类型，并放在拥有该语义的模块中供调用方共用。不能只因数字重复就提取常量，也不要求命名显而易见的索引、结构长度或计数起点；重点是让读者无需查协议或推测业务规则即可理解其用途。
- 缩写不能制造领域歧义或破坏相邻 API 的一致性。判断时同时看作用域和限定名：局部已有模块限定的 `resp` 通常足够，独立公共类型可能仍需较完整名称。重命名内部 schema 的迁移成本通常不是拒绝清晰命名的充分理由。
- 当一个模块提供一组相关能力、调用处需要多个成员，或模块名能说明成员来源时，优先 `import module` 或 `import module as alias` 并通过 `module.member` 访问；典型标准库如 `re`、`json`、`sqlite3` 通常作为模块使用。
- 少量且本身就是惯用独立名称的类型、装饰器或函数可以直接导入，例如 `Path`、`dataclass`。不要为消除所有 `from` import 而牺牲可读性。
- 从同一模块逐项导入形成长列表，或读代码必须回到文件头才能判断名称来源，是收敛为模块导入的信号。别名取当前作用域内最短且无歧义的名称，如 `import berries.game.mods as mods`。
- UI 导入同名领域模块时应显式消歧；例如 `from pist.entities import audit as backend` 可避免与 `pist.ui.entities.audit` 混淆。只有存在实际歧义时才使用 `backend`、`domain`、`game_` 等前缀，不按目录层级机械加长别名。

## 代码组织

- 以稳定职责和依赖方向判断组织，不以文件行数单独判断。一个模块同时拥有多个可独立描述、独立变化或被不同调用方复用的职责时，应拆分。
- 检查 UI、领域、游戏读取、持久化和协议边界是否混层，目录是否按工作流或领域形成可发现结构，以及拆分后是否只是制造循环依赖和转发文件。
- 同时检查多个兄弟模块是否应聚合为包，不能只检查单个模块是否需要拆分。扫描同前缀或同领域的模块，结合共同职责、内部依赖和外部调用方判断是否已形成稳定子系统；即使各模块内聚且分层正确，目录平铺仍可能没有表达领域边界。前缀相同只是检查线索，不是迁移依据；聚合时保留通用基础设施与其他领域的边界，并检查公共入口和循环依赖。
- 包的 `__init__.py` 只提供稳定公共入口，不承载实现。内部调用优先导入职责所属模块，不依赖包入口的偶然重导出。
- god module 的证据包括多个稳定职责、过多跨层依赖、修改原因彼此无关、内部区域只能靠长距离状态耦合；单纯较长但围绕一个内聚流程的模块不因此成为 god module。
- 新配置、规则、模型或服务接管职责后，检查旧派生字段、统计逻辑、兼容分支、公共导出和调用链是否仍有真实用途；确认覆盖后应连同对应测试删除，避免两个真相来源。

## 测试

- 先把测试覆盖映射到功能实现中的真实状态与错误边界；测试数量、覆盖率或完整测试通过不能证明关键分支已经覆盖。
- 测试应保护用户可见行为、数据契约、错误边界或明确的性能不变量；仅重复类型检查、标准库行为、实现逐行过程或无风险常量的测试通常没有独立价值。
- 避免断言私有函数的精确调用次数、内部容器形态、中文文案或布局细节，除非它们本身就是契约。性能回归可断言上界、随输入规模不增长或可观测查询数，给更优实现留出空间。
- 修复回归时优先增加聚焦用例，不通过改写原夹具而无意删除另一条行为覆盖。发现 dead code 时同时判断其测试是否也应删除。
- 测试夹具和 mock 应保留真实协议的关键约束；若简化后的夹具无法证明外部语义，明确标注仍需用真实样本、集成测试或人工交互复查。

## 审查输出

- 报告固定按“功能实现、代码质量、代码组织、测试”四类组织。每类分别说明发现了什么、没有发现什么，以及是否因动态入口、真实数据、数据规模或时间限制仍值得进一步检查。
- 用户只要求专项 review 时可以只展开相关 finding，但仍应判断该改动是否在其他三类引入直接回归；原结论仍成立时不重复铺陈。
- finding 给出可复现条件、影响和对应代码位置；性能项说明它是确定的无效工作、规模风险还是实测瓶颈。
- 复查提交时说明哪些问题已关闭，只详细记录仍存在或新引入的问题；测试和静态检查通过是验证依据，不代替四类审查结论。
